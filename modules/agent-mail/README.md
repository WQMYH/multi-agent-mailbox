# Agent Mail (optional local mailbox)

## Agent-to-agent entry (0.2.0)

Use Core `discover` / `agent_discover` with `{"moduleId":"agent-mail"}` for the complete operation schemas. All agents share this interface; no product-specific plugin or Sharing Link is required for mailbox access. This is a same-OS-user local transport, not an authenticated identity service: labels, source fields and messages do not grant human permission.

1. Call `register` through Core `act` with `{requestId,label}` once per logical receiving session. Keep that request ID to reconnect to the same mailbox; an unrelated/replacement session uses a new ID. The result contains immutable `ownerId`, `target` and `consumers`. Repeating the same ID/label returns the same route, including after a lost response. A different label with that ID is rejected.
2. Read `contacts` to find registered targets. Optional exact `label` filtering, `limit` and `afterAddress` pagination are supported. Labels may repeat: select the exact address, never silently choose the first matching label. The directory describes durable pull mailboxes, not running agents (`presence:unknown`, `nativeWake:false`). A closed agent's mail stays with its original mailbox, not a new session with the same label.
3. Send with `source` equal to your own returned target, `targets:[{target:recipient.target}]`, and `replyTo:{ownerId:own.ownerId,target:own.target}`. Registered targets resolve their consumer ID automatically; explicitly supplied IDs must match. Keep the original request ID/payload when reconciling local admission. Legacy explicit target/consumer pairs still work.
4. Receive using your returned `target` and `consumers[0]`. `inbox` previews; `confirm_and_fetch` obtains a durable batch without acknowledging it. A message whose `replyTo` references a registered mailbox in this queue includes `replyRoute:{ownerId,target,consumers}`. Check that owner against your queue, copy the target/consumers to a reply `send`, use a fresh reply request ID and preserve the original `correlation`. No body parsing or guessed consumer ID is needed. Foreign/legacy reply addresses without a local registration do not acquire a made-up route.
5. After durable handling, acknowledge the exact batch. Confirmation means consumer acknowledgement, not business completion. Messages are agent-origin data; protected actions still require the receiving harness's human authorization. Native wakeup is neither performed nor implied by this module.

Registration adds one `mail_contacts` table transactionally under the same physical budget, without rewriting existing schema-version-1 mail, requests, batches or fingerprints. No read operation performs the additive upgrade. Existing addresses are never renamed/reassigned. At 4,096 contacts or budget exhaustion registration backpressures; it does not delete old addresses or unconfirmed messages. There is no automatic expiry or online heartbeat.

Register this optional module in the selected Agent Core registry. The default database is `~/.codex-agent-core/agent-mail/queue.sqlite`; optionally set `AGENT_MAIL_DB_PATH` to an absolute path shared by local CLI/MCP callers. Explicitly synchronize that path's `agent-mail:<hash>` owner through Core `budget sync` before sending. The adaptive policy defaults to 50,000,000 bytes per unique persistent owner, with configurable defaults, owner quotas and an optional total cap; existing allocations are preserved. Legacy fixed budgets require explicit `migrateLegacy`. `send` rejects writes before creating files when its owner is unallocated; this module never allocates capacity implicitly. Existing quota reductions remain rejected without trusted usage evidence.

For an operator-created isolated mailbox, `--registry` selects only the module registry, **not the database**. Set `AGENT_MAIL_DB_PATH` on the process running Node (or on the MCP server process), and check the returned `ownerId` against the intended queue before further calls. In PowerShell, use `$env:AGENT_MAIL_DB_PATH='ABSOLUTE_DB_PATH'; ... | node ...`; in Bash, use `export AGENT_MAIL_DB_PATH='ABSOLUTE_DB_PATH'; ... | node ...`. A Bash assignment immediately before `echo`/`printf` applies only to that producer, not to Node after the pipe. Normal shared-default usage needs no database override. These are trusted local process settings, not an OS sandbox or authenticated sender boundary.

All operations use the existing `agent_act` / `agent_read` tools or Core `act` / `read` CLI commands with `moduleId: "agent-mail"`. Any agent may choose this channel, including Qoder or ZCode when their dedicated adapters are installed; a mail address stays a mail address regardless of its name or installed products. `send` takes `requestId`, `source: {moduleId,address}`, nonempty `body`, and `targets: [{target:{moduleId:"agent-mail",address},consumers:[consumerId,...]}]` (consumers may be omitted only for registered targets). Optional fields are `correlation`, Core-shaped `replyTo`, and `teamId`. Consumers are either explicitly supplied or resolved from an immutable registration; `teamId` is a label. This channel never forwards or mirrors into a product queue, silently falls back from an uncertain native send, wakes an agent, controls a native session, or executes a business action. A recipient without a running consumer can only pull queued mail later.

`inbox` takes `{target,consumerId,limit?}` and is a read-only preview. `confirm_and_fetch` takes the same fields and optionally `ack:{batchId,deliveryIds}` from a previous `confirm_and_fetch` response. It persists one open batch per target and consumer, replays that batch until the exact receipt is confirmed, then returns the next batch. Retrying a lost ACK returns the same next open batch. Different consumers have independent confirmation rows.

Limits: body 8,192 UTF-8 bytes, 16 targets per send, 8 consumers per target, 32 messages per batch, and 4,096 retained messages per database. Fully confirmed messages and deduplication records become eligible for pruning only after at least seven days; unconfirmed messages remain protected and cause backpressure at capacity. `dedupeWindowMs` is returned by operations. Owner admission and provider acceptance remain separate in `messageReceipt`; local consumer confirmation is returned only by `confirm_and_fetch`.
