# Agent Mail (shared local mailbox)

## Agent-to-agent entry (0.2.0)

Use Core `discover` / `agent_discover` with `{"moduleId":"agent-mail"}` for the complete operation schemas. All agents share this interface; no product-specific plugin or Sharing Link is required for mailbox access. This is a same-OS-user local transport, not an authenticated identity service: labels, source fields and messages do not grant human permission.

1. Call `register` through Core `act` with `{requestId,label}` once per logical receiving session. Keep that request ID to reconnect to the same mailbox; an unrelated/replacement session uses a new ID. The result contains immutable `ownerId`, `target` and `consumers`. Repeating the same ID/label returns the same route, including after a lost response. A different label with that ID is rejected.
2. Read `contacts` to find registered targets. Optional exact `label` filtering, `limit` and `afterAddress` pagination are supported. Labels may repeat: select the exact address, never silently choose the first matching label. Directory presence remains unknown; use `receivers` to inspect a connected native session. A closed agent's mail stays with its original mailbox, not a new session with the same label.
3. Send with `source` equal to your own returned target, `targets:[{target:recipient.target}]`, and `replyTo:{ownerId:own.ownerId,target:own.target}`. Registered targets resolve consumers automatically; explicitly supplied IDs must belong to that registration. Keep the original request ID/payload when reconciling local admission. Legacy explicit target/consumer pairs still work. Fresh mail automatically notifies connected native receivers after commit; repeated request IDs never replay a native action.
4. Receive using your returned `target` and consumer ID (`consumers[0]` for a pull registration, or the connected receiver's `consumerId`). `inbox` previews; `confirm_and_fetch` obtains a durable batch without acknowledging it. A message whose `replyTo` references a registered mailbox in this queue includes `replyRoute:{ownerId,target,consumers}`. If that message requests a reply, check that owner, copy the actual route to `send`, use a fresh reply request ID and preserve the original `correlation`. Do not automatically reply to a receipt that requests no further response. Foreign/legacy reply addresses without a local registration do not acquire a made-up route.
5. After durable handling, acknowledge the exact batch. Confirmation means consumer acknowledgement, not business completion. Messages are agent-origin data; protected actions still require the receiving harness's human authorization. A native notification references the original delivery and consumer; it contains no original body and is separate from fetch, confirmation and business acceptance.

Registration adds `mail_contacts`; native connection adds `mail_receivers`, `mail_native_intents` and `mail_dispatch_worker` under the same physical budget. Existing schema-version-1 mail, requests, batches, default subscriptions and fingerprints are preserved. Reads never upgrade the database. Existing addresses are never renamed/reassigned. At capacity or budget exhaustion, writes backpressure rather than delete protected data.

Register this optional module in the selected Agent Core registry. The default database is `~/.codex-agent-core/agent-mail/queue.sqlite`; optionally set `AGENT_MAIL_DB_PATH` to an absolute path shared by local CLI/MCP callers. Explicitly synchronize that path's `agent-mail:<hash>` owner through Core `budget sync` before sending. The adaptive policy defaults to 50,000,000 bytes per unique persistent owner, with configurable defaults, owner quotas and an optional total cap; existing allocations are preserved. Legacy fixed budgets require explicit `migrateLegacy`. `send` rejects writes before creating files when its owner is unallocated; this module never allocates capacity implicitly. Existing quota reductions remain rejected without trusted usage evidence.

For an operator-created isolated mailbox, `--registry` selects only the module registry, **not the database**. Set `AGENT_MAIL_DB_PATH` on the process running Node (or on the MCP server process), and check the returned `ownerId` against the intended queue before further calls. In PowerShell, use `$env:AGENT_MAIL_DB_PATH='ABSOLUTE_DB_PATH'; ... | node ...`; in Bash, use `export AGENT_MAIL_DB_PATH='ABSOLUTE_DB_PATH'; ... | node ...`. A Bash assignment immediately before `echo`/`printf` applies only to that producer, not to Node after the pipe. Normal shared-default usage needs no database override. These are trusted local process settings, not an OS sandbox or authenticated sender boundary.

All operations use the existing `agent_act` / `agent_read` tools or Core `act` / `read` CLI commands with `moduleId: "agent-mail"`. Any agent may choose this channel; a mail address stays a mail address regardless of its name or installed products. `send` takes `requestId`, `source: {moduleId,address}`, nonempty `body`, and `targets: [{target:{moduleId:"agent-mail",address},consumers:[consumerId,...]}]` (consumers may be omitted only for registered targets). Optional fields are `correlation`, Core-shaped `replyTo`, and `teamId`. `teamId` is a label. Messages stay in this queue. Native transports only notify operator-bound sessions; no uncertain native action is replayed or silently changed to another transport. A recipient without a reachable native receiver can still pull queued mail later.

`inbox` takes `{target,consumerId,limit?}` and is a read-only preview. `confirm_and_fetch` takes the same fields and optionally `ack:{batchId,deliveryIds}` from a previous `confirm_and_fetch` response. It persists one open batch per target and consumer, replays that batch until the exact receipt is confirmed, then returns the next batch. Retrying a lost ACK returns the same next open batch. Different consumers have independent confirmation rows.

`confirm_and_fetch` additionally accepts optional `deliveryIds` to fetch exact retained deliveries for that target and consumer. The selection must fit `limit`; the default stays FIFO. A different already open batch returns `MAIL_BATCH_OPEN` without altering it. Selection never weakens whole-batch ACK validation or consumes unrelated old mail.

Limits: body 8,192 UTF-8 bytes, 16 targets per send, 8 enrolled consumers per registered mailbox or delivery, 32 messages per batch or explicit selection, 4,096 contacts and 4,096 retained messages. Fully confirmed records become eligible for pruning after at least seven days, except protected unknown native intents. Unconfirmed messages remain protected and cause backpressure. `dedupeWindowMs` is returned by operations. Owner admission and provider acceptance remain separate in `messageReceipt`; native notification outcomes are in `send.results[].nativeDelivery`, while consumer confirmation requires `confirm_and_fetch`.

## Native receiver connection

The operator configures `~/.codex-agent-core/agent-mail-receivers.json`, or sets absolute `AGENT_MAIL_RECEIVERS_PATH` on the trusted process. Operations select receiver IDs, never arbitrary paths, URLs, scripts or credentials.

```json
{
  "schemaVersion": 1,
  "receivers": [
    { "receiverId": "agent-a", "transport": "claude-peer", "sessionId": "11111111-1111-4111-8111-111111111111", "cwd": "C:/work/project", "home": "C:/Users/operator/.claude" },
    { "receiverId": "agent-b", "transport": "kimi-server", "sessionId": "session-existing", "cwd": "C:/work/project", "home": "C:/native-home" },
    { "receiverId": "sender", "transport": "codex-host", "sessionId": "exact-codex-thread-id", "cwd": "C:/work/project", "hostConfigPath": "C:/trusted/host-config.json" }
  ]
}
```

Up to 64 unique receiver IDs and native receiving identities are permitted, with optional boolean `enabled`. `home` defaults to the product's local home. Windows Claude/Kimi drivers validate exact session IDs, canonical cwd and current process creation metadata. Stale or ambiguous sessions are unreachable; Kimi HTTP 401/403 is explicitly reported as authentication refusal. Secrets stay in native local files and never appear in mail or public results. A Codex `hostConfigPath` contains the operator issuer's existing `threadId`, `cwd`, `script` and `pipePath`; receiver `sessionId` and `cwd` select the target. The driver verifies issuer and target independently (one read when identical), keeps the issuer in native MCP call metadata and sends to the target. Targets can share one trusted issuer configuration.

| Operation | Core mode | Purpose |
| --- | --- | --- |
| `connect_receiver {receiverId,target,consumerId?,deliveryIds?}` | act | Bind an operator-configured native session to an existing registration. |
| `receivers {receiverId?,target?,afterReceiverId?,limit?}` | read | Inspect current availability without waking or consuming. |
| `deliver_pending {receiverId,deliveryIds}` | act | Explicit recovery for subscribed deliveries never dispatched. |

Omit `consumerId` to create an independent consumer, or supply that registration's default consumer. Two native sessions cannot share a consumer. Connections are immutable; a different native session needs a new receiver ID. The same native identity cannot be connected under another receiver ID, even after the operator renames its configuration: an alias cannot bypass an existing unknown intent. Receiving identity uses transport/sessionId/canonical cwd and the actual Claude/Kimi home namespace; Codex issuer paths and its unused home field do not distinguish targets. Explicit `deliveryIds` enroll and notify only those historical deliveries. Connecting or reconnecting never turns all old pending mail into new tasks. Multiple distinct native consumers read and confirm the same original message row.

Fresh sends create qualified pending notification intents. Implicit sends to a mailbox with native receivers subscribe those receivers; an unused default consumer does not acquire fresh ghost subscriptions. Explicit valid consumers stay subscribed alongside native receivers. Saved old request fingerprints and existing default subscriptions stay intact.

The common dispatcher runs detached under the current Core registration generation with one owner lease. It watches queue/config/native metadata changes and uses a ten-second availability fallback for missed events; a short CLI may exit while its offline receiver remains watched. Receivers advance independently. Disable or replacement stops the old generation before further native actions. The next authorized send or receiver connection can start a stopped dispatcher. No model polling or second message queue is used, and normal receiving needs no manual `deliver_pending` loop.

Before a native action, the same intent changes atomically from `pending` to `unknown`. Concurrent processes cannot send it twice. Native outcomes are `submitted` (Claude peer write without an ACK), `accepted` (native Kimi/Codex admission), `held`, `refused` or `unknown`. Each attempted state is retained without replay; unreachable `attempted:false` means no native action occurred and recovery may dispatch it. Native control and human approval are never bypassed. Body retrieval, exact consumer ACK and business acceptance remain separate.

Claude uses the current session's native peer key and `priority:"next"`, without impersonating a parent or child. Kimi uses its existing session/prompts API and a stable intent-derived `prompt_id`; duplicate responses never permit a replacement ID. Codex verifies `read_thread` identity and uses native `send_message_to_thread`, allowing the host to steer or start that same thread. These are thin transports behind one receiver interface, not dedicated mailbox plugins.

For private-registry staging of an existing native session, optional top-level trusted `coreClient:{cliPath,registryPath}` supplies absolute common Core CLI paths. When present, that exact CLI/registry instance governs all mail discovery, fetch, any requested reply send and ACK in the exchange; it is not merely an MCP fallback. The notification includes the current queue path for every subprocess `AGENT_MAIL_DB_PATH` and an owner check. Receivers must not mix in loaded MCP or another registry, even if it accepts the same mailbox IDs. An unavailable selected client is reported without fallback. Without `coreClient`, the normal shared Core MCP interface is used. This does not change a formal registry, copy the original body or start another model. Changing the client setting does not rebind the native session.

Checks: `node --test modules/agent-mail/adapter.test.mjs modules/agent-mail/receivers.test.mjs modules/agent-mail/standalone.test.mjs`. Native fixtures are offline evidence; a real receiving agent must still fetch the original body, confirm its exact batch and provide any requested correlated reply.
